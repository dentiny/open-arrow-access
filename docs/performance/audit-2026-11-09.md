This audit adds a reproducible benchmark matrix and splits four measured
optimizations into independent upstream PRs. None of these PRs is merged.
The benchmark PR itself changes no production code or released dependency versions.

## Method

There are 23 cases covering all six exposed formats, both ATIF JSON layouts,
full/projected reads, XML inference, FS/HTTP storage, range reads, shared provider
HTTP and fragmented line assembly. See [the methodology](README.md) for commands,
input construction, coverage and limitations.

Default cases have 20,000 generated rows, 64 KiB format input chunks and 1,024-row
output batches. Single-document ATIF instead has one trajectory with 20,000
steps. ATIF's unknown-field case adds a 4 KiB unmapped string per trajectory.
The HTTP fixture returns 16 KiB buffers. Only the FS case writes a fixture to
disk. Opening and consuming every output is timed; setup precedes timing.

The full matrix uses one warmup plus seven measured iterations. The optimization
comparison alternates baseline/optimized execution order over three fresh
processes per variant, with one warmup and 15 measurements in each process.
Reported A/B medians combine all 45 measurements per variant. Every decode
checks the expected row count; byte/range cases check returned lengths.

Whole-process CPU and peak RSS come from `wait4`, including setup, warmup and all
rounds. They are not decoder-only allocations. Fixtures and memory inputs retain
copies of the payload, and the JSON metadata generator allocates a parsed tree.
Allocator retention also makes process RSS sensitive to iteration count. There
is no cloud RTT, TLS/socket traffic or cold-disk measurement in these fixtures.

## Findings and independent fixes

1. **Buffered HTTP body growth and copies** — `service/src/http_body.rs` repeatedly
   grows a Vec while collecting responses. Reserve from a capped, validated
   Content-Length after data arrives; return a shared single buffer only after
   EOF validation. The new matrix tests empty, unknown-length, single/fragmented,
   truncated and oversized responses. The streamed download path already avoids
   this whole-body materialization and is the appropriate API for large files.
2. **ATIF root JSON roundtrip** — normalization serializes the entire typed
   trajectory into another JSON tree, including unmapped root payloads. Borrow
   extension values and materialize typed envelope fields individually. Raw JSON,
   flattened-field precedence, omitted-field validation and failed-append
   atomicity are preserved. The measured gain is targeted; this does not remove
   parsing, nested normalization or the final Arrow copy.
3. **XML record capture allocations** — the streaming reader builds a new capture
   Vec for each record. Recycle successfully consumed captures across records and
   batches, retaining capacities only up to 64 KiB. Namespace injection, error
   offsets, inference replay, byte-limit deferral and Arrow batch ownership remain
   intact. Large/small Unicode records with retained prior batches are tested.
4. **WARC header framing dispatch** — buffered complete headers still invoke an
   async line reader per header line. Scan the first blank-line terminator and
   copy that complete block once; fragmented blocks retain the original bounded
   fallback. Every input boundary, mixed line endings, body preservation and the
   4 MiB header limit are covered by regression tests.

## CPU, I/O and memory interpretation

ATIF's CPU sample repeatedly visits `normalize_field`, JSON tree construction,
Arrow builders and malloc/realloc under `append_json`. This supports a CPU and
allocation diagnosis for in-memory conversion. Inlining and Rust symbol mangling
make the sample unsuitable for assigning precise stage percentages.

The storage range workload requests 8,192 disjoint 64-byte ranges from a
19.53 MiB object: only 512 KiB is logically returned. It makes 8,193 HTTP requests
including stat. Full HTTP scans make ten range GETs plus one stat; supplying a
trusted known length eliminates that one HEAD. The disjoint case is a clear
request-amplification risk when real RTT exists. It is not evidence that the
adapter should read the gaps: bridging them changes the requested-byte contract
and may erase Parquet projection savings. No such behavior is changed here.

CSV projection retains tokenization of all input fields; the lexer still has to
find delimiters and quoted fields. JSON similarly must traverse skipped values.
Parquet projection avoids a physical column and shows a much clearer reduction
in this narrow two-column fixture. These formats have different representations
and schemas; their raw wall times should not be used to rank formats generally.

ATIF single-document mode collects a complete trajectory before conversion, and
owned WARC records buffer their bodies. Those APIs have whole-record memory
costs by design. Large-record datasets need separate size-scaling experiments
before replacing those contracts. XML inference currently converts the inferred
schema before the adapter applies a requested projection, so inferred projection
pushdown is another follow-up; it needs API/validation design rather than a
silent change in this audit.

## Scope and remaining work

The provider HTTP cases exercise common metadata/body/download paths. They do
not time every provider-specific catalogue resolver, and no real HF/Xet, S3,
other credentialed cloud service, compressed-format combination, cold disk or
production dataset is represented. Storage here is the shared OpenDAL adapter
with FS and controlled HTTP backends. Test generated input size, chunk size and
batch size against representative production objects before choosing broader
parallelism, caching or range-coalescing policies.

The existing test-support HTTP fixture fragments data into three-byte buffers;
that is useful for boundary tests but misleading as a default throughput model.
The benchmark installs its own 16 KiB transport and records the request count.
