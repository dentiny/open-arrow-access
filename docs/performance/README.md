# Local performance matrix

The `performance` bench exercises the public accessors, including opening the
reader and consuming every output. Inputs are deterministic, generated locally,
and validated by row/byte counts. Payload generation, the filesystem fixture,
transport setup and schema setup precede the timed iterations. Each case has one
untimed warmup. Timed results include opening/inference, decoding and dropping
batches; batches are consumed rather than retained. No remote datasets, cloud
credentials or external network requests are needed.

```sh
cargo bench --bench performance --all-features --no-run --locked
# Use the executable path printed by Cargo, not `cargo bench` as the binary.
python3 scripts/benchmark.py \
  --binary target/release/deps/performance-EXACT_HASH \
  --output work/baseline.json
```

Use `--cases csv json xml` to select workloads. `--rows`, `--rounds`, `--chunk`
and `--batch` control the generated row count, measured repetitions, input chunk
size and output batch size. Defaults: 20,000 rows, seven measured iterations,
64 KiB input chunks, 1,024 rows per batch. The native executable also accepts
`BENCH_ROWS`, `BENCH_ROUNDS`, `BENCH_CHUNK`, `BENCH_BATCH` environment variables.
`--list` lists the available cases. All sizes must be positive.

## Coverage and interpretation

| Path | Workloads | What it isolates |
| --- | --- | --- |
| CSV, JSON | Full and id-only projection | Decoder CPU; wide string field skipping |
| Parquet | Full and id-only projection | Range-based decoder, column pruning |
| ATIF JSON and JSONL | Full, id-only, large unknown field | Parsing, validation, normalization and intermediate JSON copies |
| XML | Explicit schema, projection, inference | Capture, parsing and conversion, including schema sampling |
| WARC | Complete physical records with owned bodies | Header parsing and record framing |
| OpenDAL FS | Whole-object sequential scan | Warm local filesystem and chunk adapter |
| OpenDAL HTTP | Unknown/known length, scattered ranges | HEAD overhead, request count and range amplification |
| Provider HTTP | Metadata JSON, buffered body, streaming download | Shared provider transport, JSON tree and body collection |
| Shared line reader | 4 KiB lines in 257-byte chunks | Cross-chunk assembly and polling |

The format inputs use the observed in-memory accessor from test-support. This
removes filesystem/network latency but includes its counters and async dispatch.
Parquet input is generated by ArrowWriter with default compression/encoding, so
its physical bytes and CPU workload differ from the text formats. Do not rank
formats by wall time alone: the schemas and record complexity also differ.

The mock transport returns 16 KiB chunks, implements HEAD and exact byte ranges,
and records requests. It has **no network RTT, bandwidth throttling, TLS or
socket costs**. A large request count identifies an I/O risk; it does not measure
cloud latency. FS scans run against the warm OS cache, not a cold disk. The
known-length HTTP case skips stat. Scattered reads intentionally request only
64 bytes every 1,024 bytes; gap-zero coalescing preserves projection savings and
does not bridge those gaps. This is not evidence that reading every intervening
byte would be preferable.

The three provider cases cover shared HTTP paths, not all provider-specific
catalogue resolvers. OpenDAL operators are configurable; this suite directly
exercises the FS and HTTP services used by local/provider reads. It does not
claim real S3, HF/Xet or other cloud measurements without representative datasets
and credentials. ATIF single-document mode generates one trajectory with `--rows` steps; JSONL
generates `--rows` separate trajectories.

## CPU and memory

The runner uses `wait4` to report **per-process** user/system CPU time and peak
RSS. On macOS RSS is in bytes; on Linux the runner converts KiB to bytes. These
figures include fixture/input construction and warmup as well as measured rounds.
They are not allocation counts, decoder-only memory, or storage physical-byte
counters. In particular, input copies and retained fixture bodies contribute to
RSS; metadata JSON generation can itself be the peak. Sequential throughput is
logical input bytes divided by median measured time. For range scans, use the
returned `units` (requested bytes), not the size of the entire source object.

Compare the same case, settings, compiler and machine. Compile everything first,
then measure without simultaneous tests/builds. For changes under normal machine
noise, alternate the baseline/optimized order in several fresh processes and
retain all samples. Do not interpret an unchanged control's timing variation as
an optimization. Use a CPU sampler alongside a separate profiling run to locate
hot stacks; do not include the sampled run in timing comparisons.

## Applying dependency optimizations locally

Keep benchmark source identical and use temporary path patches in the root
manifest, then rebuild; do not commit local paths or publish unreleased dependency
versions as though they were on crates.io:

```toml
[patch.crates-io]
atif-arrow = { path = "../atif-arrow/crates/atif-arrow" }
xml-arrow = { path = "../xml-arrow-rs/crates/xml-arrow" }
warc-rs = { path = "../warc-rs" }
```

Preserve each built executable before rebuilding the other variant. See the
accompanying local report for pinned revisions, raw measurements and limitations.

For alternating A/B trials, preserve both executable files and run:

```sh
python3 scripts/compare_benchmarks.py \
  --baseline work/performance-baseline --optimized work/performance-optimized \
  --output work/comparison.json --cases atif xml warc service/body
```

The output records executable SHA-256 hashes. The runner's working-tree revision
describes the checkout at measurement time, not the source of an arbitrary
prebuilt binary; record the build revisions and any local patches separately.
